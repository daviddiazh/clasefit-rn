# Preguntas de reflexión · Desarrollador React Native espartano

### 1. ¿Qué experiencia previa tenías usando OpenSpec o SDD?

No tenía experiencia previa usando OpenSpec ni trabajando formalmente con SDD. Para esta prueba tuve que aprender primero cómo funcionaba el flujo y qué responsabilidad tenía cada artefacto antes de empezar a implementar. Me apoyé en la documentación, algunos videos de Youtube y en la IA para entender el proceso, y fui aplicándolo durante el desarrollo de la prueba.

### 2. ¿Cómo crees que cambia el rol de desarrollador React Native antes y después de conocer y aplicar este framework?

Creo que el rol no cambia en lo fundamental, pero sí cambia la forma de abordar el desarrollo. Ya no se trata solamente de recibir un requerimiento y empezar a escribir código, sino de entender mejor el problema, definir el comportamiento y dejar claras las decisiones antes de implementar. También creo que el desarrollador debe adaptarse a nuevas herramientas y procesos que permitan trabajar mejor con IA y con otros miembros del equipo.

### 3. ¿Cómo crees que debería trabajar ahora un equipo que usa esta metodología?

Creo que el equipo debería aprovechar estos documentos como una referencia común y no como documentación que solo se crea para cumplir un proceso. Por ejemplo, se pueden definir instrucciones para escribir tests, estándares del proyecto, convenciones de ESLint o incluso procedimientos para tareas repetitivas. De esta forma, la IA y los desarrolladores tienen un contexto más claro y se reduce la necesidad de repetir las mismas decisiones en cada tarea.

### 4. ¿Qué ventajas y desventajas ves?

La principal ventaja que veo es que obliga a pensar y definir el problema antes de empezar a programar, además de dejar un contexto que puede ser utilizado tanto por otros desarrolladores como por herramientas de IA. También facilita dividir cambios grandes en tareas más pequeñas y verificables. Como desventaja, puede generar más trabajo inicial y sentirse innecesario para cambios muy pequeños, especialmente si el equipo termina documentando cosas que realmente no aportan valor.

### 5. ¿Cuándo usarías y cuándo no usarías este método?

Lo usaría principalmente para funcionalidades nuevas, cambios importantes o proyectos donde participan varias personas y es importante mantener un contexto común. También lo veo útil cuando se trabaja bastante con IA, porque tener las reglas y decisiones por escrito ayuda a que las herramientas entiendan mejor el proyecto. Para cambios pequeños, correcciones simples o tareas muy puntuales probablemente no usaría todo el proceso porque el costo de documentarlo puede ser mayor que el beneficio.
